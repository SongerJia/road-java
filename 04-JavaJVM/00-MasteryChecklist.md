## 1. JVM 内存区域？哪些线程私有？

**锚点**：《深入理解 Java 虚拟机》第 2 章 / 官方规范

- [ ] **及格**：说出 5 大区域——**线程私有**：程序计数器、虚拟机栈、本地方法栈；**线程共享**：堆、方法区（JDK8+ 元空间）；外加直接内存（不属于 JVM 管理）

## 2. 类加载过程五步？双亲委派模型？

**锚点**：《深入理解 Java 虚拟机》第 7 章

- [ ] **及格**：五步——**加载 → 验证 → 准备 → 解析 → 初始化**；双亲委派：类加载请求**先交给父加载器**，父加载不了才自己加载
- [ ] **良好**：及格 + 能说出每一步做什么（加载：读字节流生成 Class 对象；准备：分配静态变量内存并赋零值；初始化：执行 `<clinit>`）+ 三层加载器（启动 Bootstrap / 扩展 Platform / 应用 App）+ 双亲委派的**两个好处**（防止核心类被篡改、避免重复加载）

## 3. 三色标记原理？增量更新 vs SATB？

**锚点**：《深入理解 Java 虚拟机》第 3 章 / CMS 与 G1 设计

- [ ] **及格**：三色——**白色**（未访问，可能回收）、**灰色**（访问中，引用未处理完）、**黑色**（自己与引用都处理完，存活）；标记结束剩下白色 = 垃圾
- [ ] **良好**：及格 + 能解释**并发标记的致命问题：漏标**（黑色对象新增对白色对象的引用 → 白色对象被误回收）+ 两种解法：**增量更新（CMS）**记录新增引用、把黑色重新变灰；**SATB（G1）**记录删除引用、按起始快照保留
- [ ] **精通**：良好 + 能应对追问——为什么「误标」可接受（浮动垃圾，下次 GC 再收）而「漏标」致命、CMS 4 阶段（初始标记/并发标记/重新标记/并发清除）、G1 的 **Remembered Set**、增量更新为什么会多扫描

## 4. G1 和 CMS 的区别？

**锚点**：官方文档 / 《深入理解 Java 虚拟机》第 3 章

- [ ] **及格**：CMS 基于**标记-清除**（老年代，低停顿但有碎片）；G1 基于 **Region 分区**，可预测停顿，JDK9+ 默认
- [ ] **良好**：及格 + 能说出 CMS 的 4 阶段（初始标记/并发标记/重新标记/并发清除）与停顿组成 + G1 的核心思想（把堆分成若干 Region，跟踪每个 Region 的回收价值，优先回收垃圾最多的——**Garbage First**）+ 停顿可预测（`-XX:MaxGCPauseMillis`）
- [ ] **精通**：良好 + 能应对追问——G1 为什么取代 CMS（CMS 碎片化、并发清除与业务线程竞争 CPU、无法处理浮动垃圾）+ **Mixed GC**（新生代 + 部分老年代）、G1 的 Humongous 大对象处理、ZGC 和 G1 的差异（染色指针、读屏障、毫秒级停顿）

## 5. 内存泄漏排查步骤？

**锚点**：《深入理解 Java 虚拟机》第 4 章 / 线上排查实战

- [ ] **及格**：区分**内存溢出**（真不够）与**内存泄漏**（对象无法回收、占着不放）；常见泄漏场景（ThreadLocal 没 remove、静态集合一直 add、连接/流没关闭、监听器没移除）
- [ ] **良好**：及格 + 能说出排查工具——`jps`（找进程）、`jstat`（看 GC 与内存趋势）、`jmap -dump`（导堆快照）、`jstack`（看线程栈）；分析流程：**dump 堆 → MAT 分析 → 找大对象/泄漏对象的 GC Roots**
- [ ] **精通**：良好 + 能应对追问——MAT 的 Dominator Tree 怎么找泄漏根、`ThreadLocal` 泄漏的原理（Thread → ThreadLocalMap → Entry 的 key 是弱引用但 value 强引用）、线上 OOM 时怎么保留现场（`-XX:+HeapDumpOnOutOfMemoryError`）、怎么用 `-Xmx` 与 jstat 判断是泄漏还是压力过大
